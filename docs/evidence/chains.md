# Evidence chains

bluedb embeds an **append-only, verifiable evidence log** (`bluedb-evidence`) and
exposes it over HTTP at `/evidence/*`. An *evidence chain* is a per-`(tenant,
chain)` ordered log of opaque events. Each append gets a **server-assigned,
dense, gap-free sequence number**, is committed inside bluedb's serialized writer
as **one atomic, durable-before-ack write**, and — on a *verified* chain — is
folded into an **RFC 6962 Merkle tree** so anyone can later prove an entry's
inclusion and that the log only ever grew.

It is built for chain-of-custody / audit use cases: an external service records
evidence events here and gets tamper-evidence (Merkle proofs), exactly-once dense
ordering, and **GDPR-grade erasure** (redaction that crypto-shreds the payload
while keeping the proof structure intact).

!!! note "bluedb stores opaque bytes — the consumer owns the meaning"
    `type`, `payload`, and `at` are stored **verbatim** and never interpreted,
    normalized, or generated by bluedb (the one exception is `seq`, which the
    server assigns). The payload crosses the wire as **base64** (`payload_b64`)
    and is byte-exact in == out. For verifiable chains bluedb hashes a *framed
    copy* of the exact bytes — it never rewrites what you stored.

## Verified vs. plain chains

A chain's mode is fixed at creation and governs whether the Merkle machinery
runs:

| Mode | Created by | Merkle proofs | Mutability |
|---|---|---|---|
| **verified** (default) | `PUT {"verified": true}`, or auto-created on first append | yes — `digest` / `proof` / `consistency` | immutable; only **redaction** may alter an entry |
| **plain** | `PUT {"verified": false}` | no — proof endpoints return `400 E_NOT_VERIFIED` | redaction **and** hard-delete allowed |

Appending to a chain that does not exist **auto-creates it as verified**.
Re-creating with the same mode is a no-op; with a different mode →
`409 E_CHAIN_MODE_CONFLICT`.

## Append semantics

A single append takes one event **or a batch**, and for a K-event batch on chain
`C`:

- **Dense, gap-free `seq`.** The per-chain counter is read-modify-written *inside
  the same `WriteBatch`* as the entries (not a scan-`MAX`), so sequences are
  monotonic, contiguous within a batch, and never reused. A discarded batch burns
  no seq. `base_seq` is the head before the append; the first new entry is
  `base_seq + 1`.
- **Idempotency (optional `idem_key`).** A replay with the same key **and**
  identical events returns the original `{base_seq, seqs}` with no second write;
  the same key with *different* events → `409 E_IDEM_CONFLICT`. The fingerprint is
  a SHA-256 over the framed batch (byte-identity, not canonicalization) and
  includes any edge-deltas.
- **Durable before ack.** The batch is written then flushed (group-commit:
  `write(await_durable:false)` → release the writer lease → `flush()`), so an
  ack means the data survived. Reads use a point-in-time snapshot and are
  identical on the writer and on read replicas.
- **Atomic with the graph.** If an event carries `edges[]`, those graph mutations
  land in the *same* `WriteBatch` as the entry — see
  [the graph store](graph.md#append-with-edges).

## Merkle verification (verified chains)

bluedb maintains an **RFC 6962** append-only Merkle tree — the Certificate
Transparency / Trillian model — per verified chain:

- **Leaf hash** = `SHA-256(0x00 ‖ frame(type, payload, at, edges))`; **node hash**
  = `SHA-256(0x01 ‖ left ‖ right)`; the empty tree's digest is `SHA-256("")`
  (`e3b0c442…b855`).
- The incremental **frontier** (the ≤ log N perfect-subtree roots covering the
  current size) is persisted under its own key **in the same `WriteBatch`** as the
  entries, so the tree advances atomically with the log and is crash-consistent.
- `digest` folds the frontier in O(log N). Inclusion and consistency **proofs**
  are computed **on demand** from the stored leaf hashes.

**Verification is client-side.** bluedb generates digests and proofs; the
consumer verifies them with any standard RFC 6962 verifier against a digest it
trusts. A `consistency` proof shows that one digest is a prefix (append-only
extension) of a later one — i.e. the log was never rewritten.

## Erasure

Two destructive operations, keyed to the chain's mode. Both require the
`schema:admin` scope (not `data:write`).

- **Redaction (any chain)** — blanks the payload and sets `redacted: true`, but
  **keeps** `seq`, `type`, `at`, `edges`, and (on verified chains) the
  `leaf_hash`. Because the leaf hash is retained, the **digest and all proofs
  still verify** — the entry's *existence* stays provable while its content is
  gone (crypto-shred / redactable Merkle). Idempotent. This is how a verified,
  tamper-evident chain still satisfies a right-to-erasure request.
- **Hard-delete (plain chains only)** — removes the entry slot entirely. The seq
  counter is **not** decremented, so a **gap** appears (reads skip it, paging
  tolerates it). On a verified chain this is rejected with
  `409 E_VERIFIED_NO_DELETE` — dropping a slot would break the consistency proof.
  Hard-delete is genuine deniability-of-existence and, by default, also
  [retracts the entry's graph edges](graph.md#append-with-edges).

## HTTP surface

All routes are tenant-scoped (see [Multi-tenancy](#multi-tenancy)) and, when
[authorization](../operations/admin.md) is on, require the scope noted per route.

### `PUT /evidence/{chain}` — create / ensure a chain

```bash
curl -s -X PUT localhost:8081/evidence/audit-2026 \
  -H 'content-type: application/json' -d '{"verified": true}'
```

```json
{ "chain": "audit-2026", "verified": true }
```

Body `{"verified"?: bool}` (default `true`). Scope: `data:write`.

### `POST /evidence/{chain}/entries` — append events

```bash
curl -s -X POST localhost:8081/evidence/audit-2026/entries \
  -H 'content-type: application/json' \
  -d '{
        "events": [
          {"type": "access.granted", "payload_b64": "eyJ1c2VyIjoiYSJ9"}
        ],
        "idem_key": "req-7f3a"
      }'
```

```json
{ "base_seq": 0, "seqs": [1] }
```

Body: `{"events": [{"type", "payload_b64", "at"?, "edges"?}], "idem_key"?}`. Each
event may carry an `edges` array (`[{graph, src, dst, weight?, type?, op?,
merge?}]`) that is materialized into the [graph store](graph.md#append-with-edges)
in the same atomic write. Scope: `data:write`.

### `GET /evidence/{chain}/head` — current head sequence

```bash
curl -s localhost:8081/evidence/audit-2026/head
```

```json
{ "seq": 1 }
```

O(1) read of the counter (`0` for an empty/unknown chain). Scope: `data:read`.

### `GET /evidence/{chain}/entries` — read entries

- `?from=&to=` — inclusive range (defaults: `from=1`, `to=head`).
- `?after=&limit=` — page forward (`after` exclusive; server caps the page).
- no params — the full chain.

```bash
curl -s 'localhost:8081/evidence/audit-2026/entries?from=1&to=10'
```

```json
[ { "seq": 1, "type": "access.granted", "at": "", "redacted": false,
    "payload_b64": "eyJ1c2VyIjoiYSJ9" } ]
```

A redacted entry omits `payload_b64` and reports `"redacted": true`. Scope:
`data:read`.

### `GET /evidence/{chain}/digest` — Merkle digest

```bash
curl -s localhost:8081/evidence/audit-2026/digest
```

```json
{ "size": 1, "root_hash": "9f2c…(64 hex)" }
```

`size` is the leaf count; `root_hash` is the tree root (the empty-tree root for
`size: 0`). Plain chain → `400 E_NOT_VERIFIED`. Scope: `data:read`.

### `GET /evidence/{chain}/proof?seq&size` — inclusion proof

Proves entry `seq` (1-based) is in the tree of size `size` (defaults to `head`):

```json
{ "seq": 1, "size": 1, "audit_path": ["…hex…"] }
```

### `GET /evidence/{chain}/consistency?from&to` — consistency proof

Proves the size-`from` tree is an append-only prefix of the size-`to` tree
(`to` defaults to `head`):

```json
{ "first": 1, "second": 4, "proof": ["…hex…"] }
```

### `POST /evidence/{chain}/entries/{seq}/redact` — redact an entry

```json
{ "chain": "audit-2026", "seq": 1, "redacted": true }
```

Any chain; idempotent; `404` if the entry is absent. Scope: `schema:admin`.

### `DELETE /evidence/{chain}/entries/{seq}` — hard-delete an entry

```bash
curl -s -X DELETE 'localhost:8081/evidence/logs/3?retract_edges=true'
```

```json
{ "chain": "logs", "seq": 3, "deleted": true, "retract_edges": true }
```

Plain chains only (verified → `409 E_VERIFIED_NO_DELETE`). `?retract_edges=`
(default `true`) also removes the entry's graph edges. Scope: `schema:admin`.

### Named errors

| Error | Status | When |
|---|---|---|
| `E_IDEM_CONFLICT` | 409 | `idem_key` reused with different events |
| `E_CHAIN_MODE_CONFLICT` | 409 | `PUT` with a mode different from the existing chain |
| `E_NOT_VERIFIED` | 400 | a proof endpoint on a plain chain |
| `E_VERIFIED_NO_DELETE` | 409 | hard-delete on a verified chain |
| (entry / chain not found) | 404 | unknown `seq` / `chain` |

## Multi-tenancy

Every request is scoped to a tenant via the `X-Bluedb-Tenant` header (absent ⇒
the default tenant `_`). Each tenant has its own keyspace, so two tenants can use
the same chain name with zero overlap and **each chain's `seq` starts at 1 per
tenant**. With [authorization](../operations/admin.md) on, bind a token to one or
more tenants with a `tenant:<name>` scope (a `superuser` token reaches any; a
token with no `tenant:` binding reaches only the default tenant).

## Trust model

A digest fetched from the **same server** is not, by itself, proof against a
malicious operator — the operator could in principle serve a consistent but
forged view. Full irrepudiability requires the consumer to **externally anchor**
digests (periodically record `{size, root_hash}` somewhere outside bluedb) and/or
have bluedb **sign** them. v1 ships **unsigned digests + anchoring guidance**;
digest signing (a server keypair over `{size, root_hash}`) is a documented future
extension, not in v1. Within that model, the Merkle proofs are exactly as strong
as Certificate Transparency's: given a trusted digest, inclusion and consistency
are cryptographically verifiable.

## Limitations (v1)

- **Proofs are O(N), computed on demand.** Inclusion and consistency proofs are
  recomputed from the stored leaf hashes per request (streamed, memory-bounded) —
  there is **no persisted internal-node store** yet. Digests stay O(log N) via the
  frontier. Persisting internal nodes for O(log N) proofs on very large chains is
  a future optimization.
- **Unsigned digests.** See [Trust model](#trust-model) — verifiability against a
  malicious operator needs external anchoring and/or digest signing (deferred).
- **Redaction blanks the payload only.** `type` and `at` are retained; extending
  redaction to them is a future option (proofs are unaffected either way because
  the `leaf_hash` is kept).
- **Hard-delete is plain-chains-only and leaves a gap.** The seq counter is not
  decremented; verified chains reject it (it would break the consistency proof).
- **No SQL projection of the raw chain.** Unlike the [ledger](../api/ledger.md),
  evidence entries are not dual-written into a queryable table — the native read
  and proof endpoints are the contract. (The consumer projects what it needs into
  its own tables.)
- **No payload canonicalization.** bluedb frames the exact bytes for hashing and
  never normalizes them.
